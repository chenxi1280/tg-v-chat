## Relay Consistency Contracts

```text
pending -> sending -> sent | failed | uncertain
staging -> ready -> sent -> released
staging | ready -> failed -> released
```

- Outgoing dispatch, BotPushMessage dispatch, and Incoming album batch dispatch all use the durable dispatch lifecycle above. V2 creates and claims every final BotPushMessage before the second-hop remote call.
- A remote success followed by a database update failure becomes `uncertain`; uncertain is never retried automatically because doing so can duplicate the remote side effect.
- Only SessionFailure advances to another slot. DeliveryFailure leaves session health unchanged and records only the delivery result.
- All roles share the owner-only `TG_V_CHAT_MEDIA_ROOT`; spool artifacts use the media lifecycle above. Cleanup releases `sent` and deterministic `failed` artifacts only after terminal metadata is durable; artifacts tied to `pending`, `sending`, or `uncertain` dispatch remain retained.
- Account status derives from authorized slots: primary usable is active; otherwise any usable standby is degraded; all authorized slots unusable is reauth_required. Disabled/deleted accounts are not recomputed, and a never-authorized standby does not degrade a usable primary.
- Listener bindings use non-secret fingerprints `(account_id, slot_id, developer_slot, session_revision, telegram_user_id)`; encrypted or plaintext session strings are never logged as identity.
- Runtime health is role-specific: database connectivity alone is insufficient for bot/listener/worker health.
- Native forward V2 uses `collecting -> sealed -> bridge_sending -> awaiting_bot -> final_sending -> sent | failed | uncertain`; each final Bot message has its own ReplyMapping. `batch_sequence` is independent from album/media sequence. `name_only` forward origin is a Telegram privacy boundary, not a verified identity.
- Native V2 starts only when `TG_V_CHAT_NATIVE_FORWARD_V2_ENABLED=true` after all active/degraded accounts have a unique persisted `telegram_user_id`. It resolves the configured product Bot once per user-session client and excludes that Bot's final forwards and notifications from source collection. It uses the same PostgreSQL advisory-lock key for first-hop and Bot bridge consumption; returned first-hop ids are persisted only as sender-side audit evidence, while actual Bot-dialog ids are assigned in marker-scoped message-id order. Timeout and incomplete counts become explicit `uncertain`, not a silent router fallback.
- V2 account disable/delete acquires account then Telegram identity serialization, terminates nonterminal batches, and only then invalidates ReplyMapping; deletion releases the identity only after those transitions, and a stale bridge cannot recreate an active mapping after the account is unavailable.
